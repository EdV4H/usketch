# uSketch プロジェクト ポストモーテム

**作成日**: 2026-03-14
**対象期間**: プロジェクト開始 〜 開発チーム解散

---

## 1. プロジェクト概要

uSketchは、モジュラーアーキテクチャを採用したブラウザベースのホワイトボードアプリケーション。
React 19 + TypeScript + XState + Zustand を基盤とし、プラグイン可能な形状システムとDOM/Canvas描画エンジンを備えていた。

**最終到達地点**: Phase 4（パフォーマンス最適化）完了、Phase 5〜11 未着手

---

## 2. 達成できたこと（What Went Well）

### 2.1 堅牢なアーキテクチャ設計

- **18パッケージのモノレポ構成**: 関心の分離が明確で、各パッケージの責務が整理されていた
- **XState駆動のツールシステム**: 状態マシンによるツール管理は、複雑なインタラクション（選択、描画、パン、スナップ）を安定的に処理
- **プラグインベースの形状システム**: ShapeRegistry + ShapePlugins により、新形状の追加が容易な設計
- **Zodスキーマによる検証**: ツール設定のランタイムバリデーションが堅牢

### 2.2 充実した機能実装（Phase 1〜4）

- スナップエンジン（グリッド、シェイプ間、スマートガイド、45度スナップ）
- マルチセレクション、アライメント、配置機能
- Undo/Redo（コマンドパターン）
- プロパティパネル（色、透明度、シャドウ、ストローク幅）
- レイヤーパネル（基本的な階層管理）
- 背景カスタマイズ（グリッド、ドット、等角図法プリセット）
- エフェクトシステム（リップル、ピン、フェーディングピン）

### 2.3 開発基盤の整備

- **テスト**: 29のE2Eテスト（Playwright）+ 14のユニットテスト（Vitest）
- **CI/CD**: GitHub Actions（Lint、型チェック、テスト、ビルドの並列実行）
- **コード品質**: Biome（リンター/フォーマッター）+ Lefthookによるpre-commitフック
- **ドキュメント**: 56のMarkdownファイルによる包括的なドキュメント
- **自動依存関係更新**: Renovateによる自動PR生成

### 2.4 コードベースの品質

- 約39,600行の型安全なTypeScriptコード
- kebab-case命名規則の自動チェック
- Turborepoによる効率的なビルドキャッシュ

## 3. 問題点と課題（What Went Wrong）

### 3.1 プロダクトとしての完成度不足

- **Phase 4止まり**: 全11フェーズ中4フェーズしか完了せず、コラボレーション、エクスポート、永続化といったユーザーにとって重要な機能が未実装
- **「ライブラリ」として成熟したが「プロダクト」にならなかった**: 技術的には優れていたが、エンドユーザーが日常的に使えるプロダクトにはなれなかった
- **保存機能なし**: 作成したコンテンツを保存・共有する手段がなく、実用性に大きな制約

### 3.2 過剰設計（Over-Engineering）

- **18パッケージは多すぎた**: `shape-abstraction`（deprecated）、`effect-registry`、`input-manager`など、初期段階で分割する必要がなかったパッケージが存在
- **ドキュメントの肥大化**: 56のMarkdownファイルはコードベースの規模に対して過剰。実装計画書が多く、実際の開発が追いつかなかった
- **Phase 5〜11の詳細ロードマップ**: まだ着手していない将来構想を詳細に設計するのに時間を費やしていた

### 3.3 技術選択の問題

- **開発ガイドの不整合**: `docs/development/README.md`にはYarn v4と記載されていたが、実際にはpnpmを使用。ドキュメントとコードの乖離
- **古いプロジェクト名の残存**: ドキュメント内に`dom-wb-handson`（旧プロジェクト名）が残っている
- **Crop/Effect周りの未完成**: TODOが13箇所残っており、中途半端な実装状態

### 3.4 チーム・プロセスの問題

- **最終的にRenovateのみがアクティブ**: 直近50コミットがほぼ全て依存関係の自動更新。チームの開発活動が停止していた時期が長い
- **機能開発の優先順位**: スナップ/パフォーマンスに4フェーズを費やしたが、ユーザーにとってはエクスポートやコラボレーションの方が優先度が高かった可能性
- **チーム解散に至った背景**: プロダクトビジョンとの乖離、もしくはビジネス上の要因（詳細不明）

### 3.5 CI/CDの不安定さ

- `ci-failure-fix-plan.md` に記録されたCI障害（Lint、型チェック、E2Eテストの不安定さ）
- E2Eテストの SIGINT ワーカー終了問題

## 4. 学んだこと（Lessons Learned）

### 4.1 プロダクト設計

| 教訓 | 詳細 |
|------|------|
| **MVP優先** | 基盤技術の完璧さよりも、ユーザーに価値を届けられる最小限の機能セットを先に |
| **保存/共有は必須** | ホワイトボードツールにおいて保存・共有・エクスポートは「あったら良い」ではなく「なければ使えない」 |
| **フィードバックループ** | ユーザーフィードバックなしに11フェーズの計画を立てるのは無意味 |

### 4.2 技術設計

| 教訓 | 詳細 |
|------|------|
| **パッケージ分割は慎重に** | 最初は少ないパッケージで始め、必要に応じて分割する方が健全 |
| **ドキュメントは実装と共に** | 先に計画書を書いてから実装するより、実装しながら必要なドキュメントを書く |
| **XState + Zustand の組み合わせは有効** | 複雑なインタラクションの状態管理には優れた選択だった |

### 4.3 プロセス

| 教訓 | 詳細 |
|------|------|
| **自動更新だけでは保守にならない** | Renovateが動いていてもチームが開発していなければプロジェクトは死んでいる |
| **CI品質は最初から維持** | CIの不安定さは開発速度を殺す。フレーキーなテストは即座に修正すべき |

## 5. 引き継ぎ可能な資産

### 5.1 再利用推奨

- **XStateベースのツールシステム設計パターン** — 描画ツールの状態管理として非常に参考になる
- **スナップエンジン（QuadTree + SmartGuide）** — アルゴリズムとしての完成度が高い
- **プラグイン形状システム** — ShapeRegistry + 純関数プラグインの設計
- **E2Eテスト資産** — 29のPlaywrightテストシナリオ
- **座標変換サービス** — CoordinateTransformerの実装

### 5.2 注意して扱うべき資産

- **ドキュメント** — 古い情報や未実装の計画書が混在。検証が必要
- **Deprecated パッケージ** — `shape-abstraction` は後方互換のため残されているが不要
- **Crop/Effectツール** — 中途半端な実装状態。使うなら再設計が必要

### 5.3 捨てるべきもの

- Phase 5〜11の詳細ロードマップ（新プロジェクトでは白紙から設計）
- 古い開発ガイド（Yarn記載、旧プロジェクト名）
- 使われていない設定ファイルやdeprecatedコード

## 7. 総括

uSketchは**技術的には非常に優れたアーキテクチャを持つプロジェクト**だった。XState駆動のツールシステム、プラグイン形状レジストリ、モノレポ構成は、ホワイトボードアプリケーションの基盤として模範的な設計。

しかし、**プロダクトとしてユーザーに価値を届ける前にチームが解散した**ことが最大の問題。保存・エクスポート・コラボレーションといった「プロダクトとして最低限必要な機能」が未実装のまま、技術基盤の最適化に注力しすぎた。

新プロジェクトでは、この優れた技術的知見を活かしつつ、**ユーザーが実際に使える状態を最速で達成すること**を最優先とすべき。
